# 企业知识生产内置文档类型设计

## 目标

在现有文档类型管理能力上，为每个工作空间提供五种可直接使用、可查看并可派生定制的企业常用文档类型。内置类型必须是真实的租户级 `production_document_types` 记录，因为项目、资料集、文档、审核和发布流程均通过租户内文档类型 ID 形成引用，不能只在前端维护模板常量。

本设计同时消除当前写作和校验仅识别两个硬编码类型的限制，使激活版本中的章节、资料、质量、审核和发布规则成为实际执行的治理配置。

## 范围

- 为现有和新建工作空间初始化五种内置文档类型。
- 为文档类型增加来源和模板血缘字段。
- 支持查看完整配置，以及基于任意版本创建同一类型的下一草稿版本。
- 将文档类型版本快照中的配置接入写作、校验、资料冻结、审核和发布流程。
- 扩展现有文档类型管理页面、API 类型、状态和四语言文案。
- 覆盖 PostgreSQL、SQLite、后端、前端和浏览器端验收。

本次不提供文档类型删除、已激活版本原地编辑、可视化规则编排器或系统模板的自动升级覆盖。现有“软件研发基线”和“项目复盘”代码定义保留兼容能力，但不作为新工作空间的默认初始化项。

## 内置类型目录

所有内置类型初始化为 `schema_version=1`、`status=active`、`origin=builtin`。`template_key` 与下表 code 相同并保持稳定。

| code | 名称 | 必需章节 | 质量重点 |
| --- | --- | --- | --- |
| `sop` | 标准作业程序 | 目的与范围、角色职责、前置条件、操作步骤、异常处理、风险控制、验证记录、证据清单 | 步骤完整、职责明确、异常可升级、关键操作有证据 |
| `policy_process` | 制度与流程规范 | 制定依据、适用范围、术语定义、职责权限、制度要求、业务流程、审批控制、例外处理、监督机制、证据清单 | 依据有效、权责清晰、审批闭环、例外受控 |
| `product_service_guide` | 产品与服务知识 | 产品定位、核心能力、适用场景、使用前提、配置与使用、限制条件、服务标准、常见故障、升级路径、证据清单 | 适用边界明确、参数可验证、服务承诺有来源 |
| `faq` | 常见问题与标准回答 | 问题分类、适用条件、标准问题与回答、例外情况、处理建议、升级路径、来源与生效日期 | 问答一一对应、回答可执行、例外和时效明确 |
| `incident_playbook` | 故障处理与案例复盘 | 现象与影响、事件等级、止损措施、诊断过程、恢复步骤、结果验证、沟通升级、根因分析、改进行动、证据清单 | 时间线完整、根因与现象分离、恢复可验证、行动项有责任人 |

## 治理默认值

五种类型使用同一版本化 JSON 契约，创建和派生草稿时由后端完成结构校验和规范化。

- `block_schema`：版本号、必需章节及允许的块类型。允许类型必须与持久化校验器一致，包括 `heading`、`paragraph`、`code`、`callout`、`list`、`table`、`image` 以及完成基线修复后的 `fact`。
- `source_requirements`：最低有效证据数量、允许的资料来源类型、是否要求证据清单及是否允许无来源事实。
- `skill_bindings`：默认使用 `{"version":1,"skills":[]}`，不绑定不存在的 Skill 或伪造摘要。
- `workflow_plan`：默认使用 `{"version":1,"steps":[]}`，保留后续绑定真实 Skill、MCP 或工具步骤的扩展点。
- `quality_rules`：必需章节、事实证据覆盖、待确认内容、时效字段及各类型专属质量门槛。
- `review_policy`：使用当前后端支持的顺序审核步骤。
- `publication_policy`：允许的目标知识库范围、默认切片策略、知识图谱策略及发布前置条件。

v1 使用以下精确结构，所有对象拒绝未知顶层字段；数组保持声明顺序并在规范化后计算摘要：

```json
{
  "block_schema": {
    "version": 1,
    "required_sections": ["类型对应的章节名称"],
    "allowed_block_types": ["heading", "paragraph", "fact", "code", "callout", "list", "table", "image"]
  },
  "source_requirements": {
    "version": 1,
    "min_accepted_evidence": 1,
    "allowed_source_kinds": ["upload", "datasource", "mcp", "skill", "manual"],
    "require_evidence_section": true,
    "allow_unsupported_facts": false
  },
  "skill_bindings": {
    "version": 1,
    "skills": []
  },
  "workflow_plan": {
    "version": 1,
    "steps": []
  },
  "quality_rules": {
    "version": 1,
    "require_evidence_for_facts": true,
    "block_needs_confirmation": true,
    "gates": ["类型对应的稳定质量门槛代码"]
  },
  "review_policy": {
    "steps": ["business_reviewer"]
  },
  "publication_policy": {
    "version": 1,
    "target_type": "knowledge_base",
    "chunking": "inherit_target",
    "knowledge_graph": "inherit_target",
    "require_approved_review": true
  }
}
```

`quality_rules.gates` 使用稳定英文代码而不是展示文案，五种模板分别声明所需门槛；界面通过本地化映射显示名称。`review_policy.steps` 按数组顺序物化，不增加当前审核器不认识的会签或条件表达式。`publication_policy` 的 `inherit_target` 表示沿用目标知识库已快照的处理配置，不在文档类型中复制模型 ID、分块尺寸或图谱模型等易变化参数。

采用已确认的实用型审核策略：

- `sop`、`product_service_guide`、`faq`：`business_reviewer`。
- `policy_process`：先 `business_reviewer`，再 `compliance_reviewer`。
- `incident_playbook`：先 `engineering_reviewer`，再 `business_reviewer`。

缺少策略所需项目角色时，提交审核必须返回明确的角色缺失错误，不能降级为无审核发布。

## 数据模型

`production_document_types` 增加：

- `origin`：非空枚举，取值 `builtin | custom`；历史记录回填为 `custom`。
- `template_key`：可空稳定模板键；内置版本及其派生版本保留相同值，全新自定义类型为 `NULL`。

内置 v1 的 `created_by` 使用稳定的系统主体标识，不依赖用户记录先于工作空间创建。该字段不伪装成真实用户；审计记录必须能区分系统初始化和用户操作。

现有 `(tenant_id, code, schema_version)` 活版本唯一约束和 `(tenant_id, code)` 单一 active 约束继续生效。新增约束保证 `origin=builtin` 时 `template_key` 非空，并保证同一租户、模板键和版本不存在两个未删除记录。PostgreSQL 和 SQLite 的不可变触发器均扩展到 `origin` 与 `template_key`，active 或 retired 版本不能更改血缘。

## 初始化与迁移

采用强一致初始化。

### 现有工作空间

数据库迁移增加字段、约束并回填历史来源，随后为每个现有租户插入缺少的内置 v1。插入以租户和模板键为幂等边界，重复执行不会增加记录。

若租户已存在相同 code 的自定义类型，迁移保留企业数据，不覆盖、不退役，也不把它改写成内置血缘；仅跳过该租户对应模板，其余模板继续补齐。迁移测试必须覆盖该冲突分支并报告可定位的租户与 code。

### 新建工作空间

租户、默认存储后端和五个内置文档类型由同一个工作空间供应事务创建。任一写入失败，整个供应操作回滚，不产生缺少模板或缺少存储配置的半完成工作空间。所有租户创建入口继续复用 `TenantService.CreateTenant`，避免注册、自助建空间和管理员建空间产生不同结果。

模板目录由一个独立、无数据库依赖的内置目录组件提供；迁移数据是 v1 的不可变快照，运行期供应和写作校验复用同一结构定义。后续模板升级必须通过新的 schema version 和独立设计实施，不自动替换企业已激活的自定义版本。

## 版本生命周期

- 内置 v1 创建后立即 active，且与其他 active/retired 版本一样不可原地修改或删除。
- 管理员或所有者可以从任意内置、自定义、active 或 retired 版本打开“基于此版本创建草稿”。
- 派生草稿复制全部配置，保持 `code` 和 `template_key`，将 `origin` 设置为 `custom`。
- 后端在事务内锁定该租户和 code 的版本序列，并计算 `max(schema_version)+1`；客户端不能指定派生版本号。
- 并发派生请求得到不同的递增版本；同一幂等键重试返回同一草稿。
- 激活派生草稿时，仓储在同一事务内退役当前 active 版本并激活目标草稿。
- 全新自定义类型继续使用现有创建入口，`origin=custom`、`template_key=NULL`，由调用者提供从 1 开始的版本号。

## API 与权限

现有列表、详情、创建和激活接口继续保留，响应增加 `origin` 与 `template_key`。

新增派生草稿命令接口，以基础版本 ID 为路径参数，正文只接收允许修改的名称、描述和七类治理配置。后端从基础版本读取并锁定 `tenant_id`、`code`、`template_key` 与下一版本号，拒绝跨租户基础版本。接口沿用 `Idempotency-Key`，成功审计记录基础版本 ID、新版本 ID 和操作者。

查看权限保持所有有效租户成员可用；创建、派生和激活仅限 `admin/owner`。前端只负责操作可见性，后端仍是最终授权边界。

## 页面与交互

现有文档类型管理表格保持紧凑布局，新增“来源”列并使用“内置/自定义”标签。每行增加“查看配置”；active 和 retired 版本对有管理权限的用户显示“基于此版本创建草稿”，draft 继续显示“激活”。

查看配置使用只读抽屉，先展示章节、资料要求、审核链和发布策略的可读摘要，再提供七个原始 JSON 分区用于审计和排障。

派生操作复用现有创建抽屉并预填基础版本配置。`code`、`template_key` 和版本号只读，版本号显示为“提交时自动生成”；用户可以修改名称、描述和治理配置。提交失败时保留输入，版本冲突时刷新基线后允许使用同一编辑内容重试。

普通“创建草稿”继续创建新的自定义类型。页面不提供删除，也不允许编辑已存在的草稿；需要修改草稿时，从所需基础版本重新派生，避免增加本次范围外的可变草稿更新接口。

## 执行语义

激活版本在创建运行时被完整快照。后续写作、校验、审核和发布只使用该运行或文档绑定的版本快照，不读取后来激活的新版本。

- 写作器使用 `block_schema.required_sections` 和质量门槛构造提示，不再通过 code 查找两个硬编码模板。
- 版本校验器从文档类型快照读取必需章节、允许块类型、事实证据和待确认规则。
- 资料集进入 frozen 前执行 `source_requirements`，不满足时返回结构化问题。
- 审核提交继续物化 `review_policy.steps`，并在创建文档类型时提前拒绝空步骤、重复角色和未知角色。
- 发布命令根据 `publication_policy` 校验目标知识库、切片和知识图谱配置；不允许仅保存但不执行的发布规则。
- `skill_bindings` 和 `workflow_plan` 继续使用现有摘要绑定和规范化校验，不为内置模板添加占位 Skill。

## 错误处理

- 模板目录自身配置无效时，测试和启动校验必须失败，禁止悄悄创建不可用模板。
- 工作空间供应失败返回原始受控错误并回滚全部新增记录。
- 同名历史自定义类型始终优先保留，迁移不得重写企业定义。
- 派生草稿的权限、租户、基础版本状态、JSON 契约或并发检查失败时，不写审计成功记录。
- 缺少审核角色、资料不足、质量规则失败和发布目标不允许分别返回稳定错误码，前端展示可操作信息。
- active/retired 定义的不可变性同时由服务层和数据库触发器保护。

## 基线前置修复

实施前先处理两个已确认的仓库基线问题：

1. `internal/database/production_migration_test.go` 引用了不存在的 PostgreSQL `000075_knowledge_production_projection_integrity` 和 `000076_production_projection_failure_recovery` 文件，而当前 `000075` 已被临时文档迁移占用。必须先恢复或重编号该迁移链，再选择本功能的 PostgreSQL 与 SQLite 迁移编号。
2. 写作提示当前要求事实声明使用 `block_type=fact`，但持久化版本校验器会把 `fact` 判为不支持。必须统一写作输出契约和校验器后再验收内置模板写作流程。

这两项属于功能可用性的必要修复，不视为无关重构。

## 测试与验收

### 数据库与后端

- PostgreSQL、SQLite 字段、默认值、检查约束、唯一索引和不可变触发器对等。
- 现有租户回填五种模板、重复迁移幂等、同名自定义类型保护及 down migration 行为明确。
- 新建工作空间精确生成五个 active 内置类型；注入任一步失败后租户、存储和类型记录均不存在。
- 内置目录的五种 code、章节、质量门槛和审核顺序采用精确值测试。
- 七类 JSON 契约在创建和派生时执行成功、边界和非法输入测试。
- 并发派生生成唯一递增版本；幂等重试不重复创建；跨租户和低权限调用被拒绝。
- 激活后旧版本 retired，新版本 active，历史项目和运行仍引用原快照。
- 资料、写作、校验、审核与发布分别证明使用版本快照中的规则，而不是当前全局模板。

### 前端与浏览器

- API 类型、来源标签、查看配置、派生表单、权限和失败重试具备聚焦单元测试。
- 中文、英文、韩文、俄文包含完整文案，不显示未翻译 key。
- 前端全量测试、类型检查和 Vite 构建通过。
- Playwright 覆盖内置列表、只读配置、派生草稿、激活替换、只读角色和服务端失败保留输入。
- 桌面端和移动端截图验收无页面级横向溢出、按钮遮挡或文本截断；表格只在自身容器内横向滚动。

## 完成标准

- 无历史 code 冲突的新旧工作空间均拥有五个可选择的 active 内置文档类型。
- 用户可以查看模板配置、直接创建项目和文档，并由 AI 按该类型生成结构化内容。
- 管理员可以基于模板创建自定义新版本并安全替换 active 版本。
- 资料、质量、审核和发布策略均有后端执行证据，不以界面展示代替治理生效。
- PostgreSQL、SQLite、后端、前端和浏览器回归通过，功能分支可在本地完整运行和验收。
